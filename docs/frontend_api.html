01四个 workflow 文件

位于 example_workflows/api/。四份文件的图结构完全相同，只有模型与任务类型不同。

文件任务UNETTurbo LoRA
api_t2v.json文生视频fl2vafl2v_turbo_4step
api_i2v.json图生视频fl2vafl2v_turbo_4step
api_fl2v.json首尾帧生视频fl2vafl2v_turbo_4step
api_r2v.json参考主体生视频ref2varef2v_turbo_4step
不要混用

UNET 与 Turbo LoRA 必须配套。把 ref2v_turbo 挂到 fl2va 上（或反过来）不会报错，但会直接出噪声画面。后台不要动 node 1 和 node 25 的模型名。

关于 refine

文件里残留了 node 18 / 20 / 21 / 22 / 23 / 24（二采放大链路），但它们没有连到任何输出，ComfyUI 不会执行。可以忽略，也可以整段删掉让 JSON 更干净。

02提交与回调

标准 ComfyUI HTTP + WebSocket 协议，额外多两个插件自定义事件。

提交任务

POST http://<host>:8189/prompt
Content-Type: application/json

{
  "prompt": { ...改好的 workflow JSON... },
  "client_id": "<前端生成的 uuid>"
}

→ 200 { "prompt_id": "b1f0...", "number": 3 }

订阅进度

ws://<host>:8189/ws?clientId=<同一个 uuid>
事件来源用途

minimax_director_progress插件分段进度，见下方 payload
minimax_director_preview插件逐帧预览图（base64 JPEG），可做实时预览

minimax_director_progress payload

{
  "node_id": "12",
  "segment": 2,                    // 当前第几段（从 1 开始）
  "segment_total": 5,              // 本次要跑几段
  "timeline_segment": 2,           // 在时间轴上的序号
  "timeline_segment_total": 5,
  "partial_run": false,            // 是否只跑了部分段
  "phase": "sample",               // prepare / sample / decode / finish
  "phase_label": "采样",
  "phase_value": 12,
  "phase_max": 20,
  "overall_value": 6.6,
  "overall_max": 15,
  "remaining_segments": 3,
  "frames_label": "0–124",
  "task_key": "t2v"

前端进度条建议直接用 overall_value / overall_max，它已经把「段数 × 阶段」折算好了。

取结果

GET http://<host>:8189/history/<prompt_id>

→ outputs["7"]  // SaveVideo 节点，内含输出文件名与子目录
→ outputs["8"]  // 运行报告文本：分段计划、每段任务摘要、段间引导状态

拿到文件名后用 GET /view?filename=...&subfolder=...&type=output 下载。outputs["8"] 的报告文本很适合写进任务日志，排查问题时能直接看到每段实际用了什么参数。

04Director 节点参数（node 12）

字段类型说明
task_typestring任务类型显示名。仅作兜底，真正生效的是 timeline_data.global.taskType，两处必须一致

05timeline_data 结构

这是整个对接的核心。它是一个 JSON 字符串，不是对象——写进 node 12.inputs.timeline_data 前要先 JSON.stringify()。

顶层字段

editMode"segment"每段独立提示词。用 "global" 则所有段共用 global.prompt
timelineMode"prompt_batch"t2v / i2v / r2v 多镜头模式；fl2v 用 "fl2v"

"global": {
  "taskType": "t2v — 文生视频(Text to Video)",   // ← 真正决定任务类型
  "prompt": "",                                  // editMode=segment 时作为段内空提示词的回落
  "refs": [],
  "refAudios": [],
  "refVideos": [],

taskType 必须逐字一致

是带中文说明的完整字符串，不是 "t2v"：

  • "t2v — 文生视频(Text to Video)"
  • "i2v — 图生视频(Image to Video)"
  • "fl2v — 首尾帧生视频(First-Last Frame)"
  • "r2v — 参考主体生视频(Reference to Video)"

中间是 em dash（—），不是普通连字符。直接从导出的 JSON 里复制，不要手打。

对应关系

totalFrames = 620 = 124 × 5，同时 node 12 的 total_frames 也要写 620，width/height 写 864/480。三处对不上会按时间轴里的值跑，容易和预期不符。

导出文件里的残留字段

现有 JSON 的 timeline_data 里还有 keyframes、shots、batchWorkspaces、videoClips 等字段，那是画布 UI 的暂存数据。前端整条重新生成 timeline_data 即可，不需要保留这些（fl2v 除外，它要用 shots）。

06帧数换算规则

MiniMax H3 的帧数必须落在 17k + 5 网格上，否则会被强制向上取整，实际时长与请求不符。

function alignFrames(seconds) {
  let n = Math.max(5, Math.ceil(seconds * 24));
  while (n % 17 !== 5) n += 1;
  return n;
}
请求秒数原始帧数对齐后实际时长
1 秒24391.63 秒
2 秒48562.33 秒
3 秒72733.04 秒
4 秒961074.46 秒
5 秒1201245.17 秒
6 秒1441586.58 秒

合法值序列：5, 22, 39, 56, 73, 90, 107, 124, 141, 158, 175 …

建议

前端 UI 上直接给档位选择（3 秒 / 5 秒 / 6.5 秒），而不是让用户填任意秒数——否则用户填 4 秒拿到 4.46 秒，会当成 bug 报上来。单段建议不超过 124 帧，更长的内容拆成多段配段间引导，效果和显存都更好。

07段间引导

把上一段结尾的运动（和音频）钉进下一段的采样起点，让多个镜头看起来是连续的一条镜头，而不是硬切。

字段位置取值
continuityEnabledoutputtrue / false
continuityOverlapFramesoutput只接受 5 / 22 / 39 / 56，推荐 22
continuityFromPrev每个 segment第 0 段必须 false；其余 true = 衔接，false = 这里硬切
三条硬规则
  • continuityOverlapFrames 填其他数值会被吸附到最近的档位，不会报错。填 20 会变成 22，填 30 会变成 39。
  • 段数少于 2 时段间引导自动关闭，单镜头下这两个字段完全无效。
  • 上下文帧数越大衔接越顺，但每段的采样长度也会变长（更慢、更吃显存）。22 是官方基线，先用它。

混合硬切

想让第 3 个镜头是一次转场硬切、其余保持连贯，只需把 segments[2].continuityFromPrev 设成 false，总开关保持 true。这样 1→2、3→4、4→5 衔接，2→3 硬切。

08单镜头模式

和多镜头是同一份 JSON、同一个接口，只是 segments 数组里只放一个元素。

"totalFrames": 124,
"segments": [
  { "id": "s1", "start": 0, "length": 124, "frameCount": 124, "durationSec": 5,
    "prompt": "……", "negativePrompt": "bad video",
    "taskType": "", "refs": [], "genImage": { "imageFile": "" },
    "continuityFromPrev": false, "refImageSize": "match" }
]

output.continuityEnabled 留 true 也没关系，段数不足会自动失效。前端不需要为单镜头做特殊分支。

09图片的两种传法

i2v 和 fl2v 需要传图。两条路都支持，base64 可以完全省掉上传步骤。

方式 A：先上传，再引用文件名

POST http://<host>:8189/upload/image
Content-Type: multipart/form-data
  image: <file>
  type: input

→ { "name": "abc123.jpg", "subfolder": "", "type": "input" }

然后把 name 填进 imageFile。

方式 B：直接传 base64

"genImage": { "imageB64": "data:image/jpeg;base64,/9j/4AAQ..." }

不落盘、少一次往返。对前端来说通常更简单。

各任务的挂载位置

任务字段路径说明
i2vsegments[i].genImage.imageFile
segments[i].genImage.imageB64		该镜头的起始画面
fl2vshots[i].startImage
shots[i].endImage		各含 imageFile / imageB64 / width / height。首帧必传，尾帧可选
r2vsegments[i].refs[]每项 { "index": 0, "imageFile": "..." }，index 对应提示词里的 <Picture 1>（index 从 0 开始）
r2v 的提示词引用

参考图在提示词里用 <Picture 1>、<Picture 2> 引用，参考视频用 <Video 1>，参考音频用 <Audio 1>。序号从 1 开始，而 refs 数组里的 index 从 0 开始——差一位，前端拼提示词时注意。

10预览版与成片

同一份 workflow，只改三个数字。seed 保持不变，预览和成片的构图才会一致。

width × heightstepsseed
预览480 × 2728任务创建时生成，存下来
成片864 × 48020与预览相同
改分辨率要改四处

宽高在四个位置出现，必须全部同步：

  • node 12.inputs.width / height
  • timeline_data.width / height
  • timeline_data.output.width / height
  • timeline_data.refMaxSize（写长边）

并且宽高都必须是 32 的倍数。480 × 272 与 864 × 480 都满足，且比例接近，可以直接对应。

11提交前自检

后台在拼完 JSON、POST 之前跑一遍这些断言，能挡掉绝大多数线上问题。

  • node 12.task_type 与 timeline_data.global.taskType 完全相同
  • 每个 segments[i].length % 17 === 5
  • segments[i].start 等于前面所有段 length 的累加
  • totalFrames === 各段 length 之和 === node 12.total_frames
  • width 和 height 四处一致，且都能被 32 整除
  • segments[0].continuityFromPrev === false
  • continuityOverlapFrames ∈ {5, 22, 39, 56}
  • clear_vram_between_segments === true（不是空串）
  • node 12.inputs 里没有 refine 字段
  • timeline_data 是字符串，不是对象
  • i2v / fl2v / r2v：每个镜头的图都挂上了

12常见错误

现象原因处理
改了 task_type 但跑出来还是旧任务 只改了 node 12 的 widget，timeline_data.global.taskType 没跟着改 以 timeline_data 为准，两处一起改
视频比请求的长 帧数没对齐 17k+5，被向上取整 提交前用 alignFrames() 处理
多段跑到一半显存溢出 clear_vram_between_segments 是 false 或空串 改成 true
画面全是噪声 Turbo LoRA 和 UNET 不配套 r2v 用 ref2v_turbo，其余用 fl2v_turbo
镜头之间硬切，没有衔接 段数不足 2，或 continuityFromPrev 是 false，或总开关没开 查 outputs["8"] 运行报告，里面会写明段间引导实际是 ON 还是 OFF
提交后没反应、秒返回旧结果 整个 prompt 与上次完全一致，命中 ComfyUI 执行缓存 正常情况 seed 或提示词会变，不会触发；如需强制重跑，改一下 seed
r2v 提示词里的 <Picture 2> 不生效 refs[].index 从 0 开始，提示词序号从 1 开始 <Picture N> 对应 index = N - 1
